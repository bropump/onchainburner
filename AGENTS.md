# Onchain Burner — Fixed Engineering Decisions

**What this file is.** Every decision here is FIXED and was made deliberately,
usually after measuring something. Several entries reverse an earlier decision
and say so; where that happens, the reversal is the current rule and the
superseded text is kept only so nobody re-derives the old answer. Treat a rule
you disagree with as something to raise, not something to quietly "fix" — most
of them exist because a plausible-looking simplification was tried and broke
something.

**Orientation for a reader or an agent starting here:**

**The one idea everything rests on.** A vault's configuration IS its address:
`PDA(["burner", launch_mint, target_0..target_{n-1}, bps_blob], PROGRAM_ID)`.
There is no config account, no init, no update, and no withdrawal instruction.
Change any mint or weight and you derive a different address — so a funded
vault can only ever execute the configuration it was derived from. Most of the
rules below are consequences of that.

**Load-bearing invariants that must never be weakened:**

- The burn PDA signs exactly four things: a System transfer into its own WSOL
  account, `SyncNative`, the Jupiter route, and `BurnChecked`. A fifth signed
  CPI reopens the entire custody argument.
- Lamport conservation is an exact equality, not a tolerance:
  `after = before − authorized_input + validated_pump_credit`.
- Client-visible error codes 6000..=6038 are append-only.
- `FORK_DEX_PROFILE=pool` is mandatory for any fork burn measurement.

## Production framework

- **The production artifact is SBPFv3.** The reproducible wrapper pins
  `cargo-build-sbf 4.0.0`, `platform-tools v1.53`, and `--arch v3`, then
  independently requires ELF flags `3`. SBPFv2 still executes and can still be
  deployed on mainnet while SIMD-500 is inactive, but Anza has deprecated
  v0/v1/v2 deployment and schedules the block with Agave 4.3. A production
  release must not depend on that temporary compatibility window.
- **The production Solana program uses Pinocchio exclusively.** The retired Anchor implementation has been deleted; it is not a build, test, reference, IDL, or deployment target. The production crate at `programs/burner` is the sole authority for program behavior, instruction layouts, constants, and append-only client error codes 6000..=6038.
  - Review burden now falls entirely on the Pinocchio program. It has had a line-by-line adversarial review of `split.rs` and its shared helpers (no path found to stealing vault SOL or tokens, burning the wrong amount or token, redirecting output, or bypassing the quote authority), plus 22/22 adversarial cases rejected on a Surfpool fork with the vault provably untouched in every one.
  - Two review findings were fixed rather than accepted: a comment in `validate_jupiter_route` that still described the old index-1-only signer rule and was therefore false, and the absence of a post-route re-assertion of the WSOL account's authority (a `SetAuthority` there would have drained the resting balance and bricked the vault permanently).
  - A third finding was fixed: the post-route re-assertion checked the WSOL account's owner-authority but not its `delegate` (bytes 72..108) or `close_authority` (129..165). Neither moves a balance, so every other postcondition passed, but a route granted the PDA's signature could `Approve` a delegate or `SetAuthority(CloseAccount)` and leave a standing claim for a LATER transaction. `verify_no_standing_claims` now rejects both (6035 `TokenAccountEncumbered`), on entry and again after the route, for the WSOL account and each target ATA. Bounded exposure either way -- the WSOL balance rests near zero and ATA rent is re-creatable -- and only reachable by a hostile program at the pinned Jupiter id, but it is cheap to close and it is what substantiates the claim that the postconditions catch everything the PDA's signature can do.
  - Independently confirmed during that review: all six base58 constants decode to the pubkeys their comments name; both instruction discriminators and the Jupiter `route`, `BurnChecked`, `SyncNative`, and System `Transfer` opcodes are correct; `token.rs`'s byte offsets match `spl-token 7.0.0`'s own `array_refs!`; the frozen-account asymmetry correctly reverts rather than skipping; and pinocchio 0.11.2's `Rent` really does return half the correct floor, so the hand-rolled `rent_minimum_balance_zero_data` must not be "simplified" back to it.
  - A Token-2022 mint carrying an extension unknown to `spl-token-2022` 6.0.0 fails closed as 6013 `InvalidMintData` rather than 6024, because the TLV decoder errors before the allow-list is reached. Observed live with the tokenised-equity mint TSLAx. Safe, only the classification is imprecise.
- **Every Token-2022 `TransferHook` is refused (6024), including an INERT one whose program id is unset, except one exact `$PUMP` identity.** A generic hook that is inactive today can be activated by its hook authority after the vault is funded and brick every future burn, so generic hooks remain refused. The explicit `$PUMP` exception pins all three live fields: mint `pumpCmXqMfrsAkQ5r49WcJnRayYRqmXz6ae8H7H9Dfn`, hook authority `DMdBa812dBW1CHVhmTyUyVcrBnSbZbfoFC7U14k4riH1`, and hook program id `None`. This is not a generic inert-hook allowance: the authority is a PDA owned by the verified `pump-fun/transfer-hook-authority` program `333UA891CYPpAJAthphPT3hg1EkUBLhNFoP9HoWW3nug`; that program's complete instruction module is empty and its mainnet upgrade authority is `None`, so it cannot be changed to sign an activation later. Any changed `$PUMP` field and every other hook mint still fail 6024. Tokens with transfer-hook taxes remain unsupported.
  - `scripts/security-guards.ts` runs only against the production Pinocchio deployment. It covers the route-account pins (6006), the refused legacy route discriminator (6005), both Jupiter v2 fee channels (6007), and encoded input mismatches (6008) for direct and shared-account routes. Attribution comes from the innermost `Program <id> failed: custom program error: 0xN` frame, which prevents Jupiter or AMM errors from being credited to the burner.
  - The end-of-call intermediate sweep now compares against a BEFORE-snapshot. It previously asked "is this account the vault's?" only after the route, so a hostile program at the pinned Jupiter id could `SetAuthority` an intermediate away from the PDA precisely so the sweep skipped it, and keep whatever it held. `snapshot_pda_token_accounts` records the vault-owned route accounts before any leg runs; afterwards each must still be vault-owned, empty, and free of standing claims. Not reachable under the honest Jupiter program, but it was the last hole in the hostile-Jupiter claim.
  - Known gap, NOT yet closed: no adversarial test places a hostile program at the pinned Jupiter id to prove the widened PDA signer grant cannot `assign`, `allocate`, or `transfer` the vault out from under the postconditions.
  - The production quote service lives in `quote-service/`. It is a convenience builder and optional relay, not a gate: there is no quote authority and it signs nothing. Releases must exercise the exact mainnet artifact on a fork before deployment (`pnpm test:service-fork`).
  - SUPERSEDED: the caller-paid co-sign rules below were enforceable only while a quote authority existed. The program is fully keyless; anyone may build and submit a burn. Sandwich exposure is bounded only by the on-chain floor.
  - The TEST HARNESSES were themselves audited, and that audit found more than the program review did. Two of the 22 adversarial cases were passing vacuously, so "22/22" overstated the real coverage:

It also computed the rejecting program and never asserted it, so an error raised by Jupiter or an AMM (all 6000-based) could be credited to the burner. Both are fixed: a case now passes only if the BURNER rejected it with the SPECIFIC expected code and nothing moved.

    - `understated-route-account-count` cannot reach the guard it named: starving ANY leg's Jupiter CPI of an account kills the transaction before the end-of-call `route_cursor != route_pool.len()` check (verified on both the first and last leg). That guard is covered from the opposite direction by `extra-unaccounted-account-appended`, which does produce 6006.   - The crate now has host-side unit tests (`npm run test:unit`, 79 passing) covering the byte layout the whole program rests on -- amount at 64..72, decimals at 44, `is_initialized` at 45, `is_native` at 109..113, the frozen-account asymmetry, and wrong-mint vs wrong-authority. They are also the ONLY coverage of 6035, which no client-side test can reach: a delegate or close authority can only be installed by the account's own owner, i.e. the PDA, so on chain it is reachable solely by a program executing as Jupiter. **The crate is now fuzzed, and the fuzzing is mutation-proven rather than assumed.** `proptest` covers the host properties and `mollusk-svm` executes the REAL SBPFv3 artifact, which matters because a panic there is an abort and an out-of-bounds read is an access violation. Campaign: 8 host properties x 100,000 cases, a 410,000-point exhaustive sweep of the division identity (every bps 1..=10000 x 41 boundary totals including `u64::MAX`), plus **300,000 arbitrary instructions and 100,000 arithmetic probes against the artifact** (seed 20260821). Result: **~1.2M executed cases, zero program defects**; every artifact outcome was a named `Custom(6000..=6038)`, never an abort or an unnamed error. `split.rs` went from ZERO tests to 10 -- it was the worst-covered file and it is the one that parses caller-controlled bytes. Detection power was proven by MUTATION, not claimed: replacing the per-leg floor division with half-up rounding turns two properties red immediately (proptest shrinks to `total = 2`), and a bounds-filter off-by-one is caught only by the structured-corruption generator, which is why that generator exists. The artifact's own division is observable because the program pins each leg's embedded Jupiter `in_amount` (6008) BEFORE the route-account pin (6006), so a 128-bit-reference prediction fed as `in_amount` yields 6006 on agreement and 6008 on disagreement. `npm run fuzz` / `npm run fuzz:host`; longer campaigns via `PROPTEST_CASES=... BURNER_FUZZ_ITERS=...`. All dev-only: artifact unchanged at 70,984 bytes, sha `500fe941`, ELF flags 3. NOT covered: anything post-CPI (6017/6018/6020/6022/6023/6025), which is the hostile-Jupiter fixture's territory.
  - `verify_no_standing_claims` and `freeze_authority_is_none` now carry their own explicit length checks (returning 6014/6013, the same codes their guarding callers already produce for short data) rather than relying on caller ordering to avoid a slice-index abort; proven zero-behaviour-change by walking every call site, and the binary got 184 bytes SMALLER (70,984, sha `500fe941`) because LLVM drops the implicit panic paths.
  - **The hostile-Jupiter Mollusk suite now works: 9/9 cases, each rejection authored by the burner and each asserting the vault rolled back byte-identically** (`scripts/test-mollusk-hostile-jupiter.sh`, `npm run test:hostile-jupiter`, also wired into `ci:pinocchio`). It installs a malicious program at the pinned Jupiter id and drives the real SBPFv3 artifact, producing 6019, 6012 x2 (`Assign` and `Allocate` on the vault), 6035 x2 (delegate and close authority installed by the route), 6018, 6020, and 6023 x2 -- the second 6023 being the `SetAuthority`'d-away intermediate, which is precisely the case the BEFORE-snapshot (`snapshot_pda_token_accounts`) exists to catch.
    - Root cause of the fixture's long-standing `Custom(10)`: it "consumed" the input with SPL Token `Burn` (opcode 8) on the NATIVE WSOL account, which SPL Token refuses (`NativeNotSupported`), so the fixture aborted inside its own first CPI before any burner postcondition ran. Fixed by transferring the WSOL to an attacker account (opcode 3) instead.
    - **CORRECTION to an earlier claim in this file: 6017, 6022 and 6025 are NOT mid-route postconditions and CANNOT be triggered by a hostile route.** Verified in source, not argued: `fund_wsol` (swap_and_burn.rs:222) runs BEFORE `invoke_jupiter_route` (:223), so nothing the route does can produce 6017; `burn_target` burns exactly the `target_after` read moments earlier with nothing executing in between, so the post-burn balance is always zero -- probed directly, an over-depositing route makes the whole burn SUCCEED rather than raise 6022; and 6025 is a pre-route admission check in `validate_target_account` that is never re-parsed after the route. All three are defensive invariants. None was weakened to force a test. 6025 is covered instead by a host unit test (a Token-2022 ATA carrying `MemoTransfer`), the same idiom already used for 6035.
    - So the genuinely route-reachable postconditions are **6018, 6020 and 6023**, and all three are now covered. Every other code is asserted against the Pinocchio build by the fork suites (`split-negative` 29/29, `security-guards` 10/10, `e2e-admission-onchain`, `vc-validate-config`/`vc-consistency`, `e2e-atomicity`) or by the host unit tests.
- Pinocchio was selected after a measured side-by-side prototype showed a 79% smaller artifact, 79% lower deploy rent, and 25% lower average compute with equivalent rejection behavior. That prototype is historical evidence only and has been deleted. The residual cost of Pinocchio is hand-written validation, so every security review, red-team exercise, and adversarial test must run against the production crate itself.

## Immutable burner architecture

- A Pump launch mint is a namespace, and may also be a burn target. The original rule that the launch token is "never bought, sold, or burned by this program" was reversed explicitly by the user, who wants a creator's own launch token to be the majority burn (e.g. own launch 70% / NEIRO 15% / $PUMP 15%). Nothing in the program privileges or forbids the launch mint as a target: it is one entry in the configured target list like any other, and is subject to the same Token-2022 guard, ATA pinning, slippage floor, and burn-to-zero postcondition. Verified on a Surfpool fork with a real Pump token as both namespace and 70% majority leg (177,909 CU) and at 50/25/25 (185,463 CU).
- Pump fees enter the burner vault as native SOL initially.
- **The supported funding source is a NORMAL Pump launch. Mayhem, cashback, agent, and non-SOL (`quote_mint`) launches are OUT OF SCOPE.** Normal launches are the only kind that delivers native SOL directly to the vault PDA. The supported flow is **normal Pump launch -> creator fees as SOL to the PDA -> swap -> burn**, and nothing else.
  - **We are NOT the creator, and the mode is not ours to choose.** The product is permissionless in both directions: anyone launches on Pump, anyone derives and sets up a burner vault, and the launch's creator points their fee share at that vault -- either after launching, or in the same setup. Because the launch already exists (or is created by someone else) by the time a vault is pointed at it, an unsupported mode is something to DETECT, never something we can prevent at `create_v2`. Any earlier note in this file claiming we set the mode at create time was wrong and is superseded.
  - **This makes the curve check the PRIMARY control, and it is load-bearing.** A sample of 22 recent Pump launches read off mainnet found ~45% (10/22) already carry `is_cashback_coin`, ~9% mayhem, and ~5% a USDC quote mint. Cashback and USDC-quote both fund the vault with ZERO. So the common case -- a creator in good faith pointing a fee share at a correctly derived vault -- silently delivers nothing, and does so for something close to half of all launches. Whatever performs vault setup MUST read `PDA(["bonding-curve", launch_mint], 6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P)` and refuse when byte 81 (mayhem) or byte 82 (cashback) is set, or bytes 83..115 (quote mint) are not the System default.
  - This is a LIVENESS and product-correctness problem, not a custody one. No funds are ever at risk, because no funds ever arrive: the creator's fees go to buyers (cashback) or to a USDC ATA (non-SOL quote) instead of to the vault. Nothing reverts, so without the curve check the creator's only signal is that the vault stays empty forever.
  - **The check must NOT be moved on chain.** The vault is an ordinary System account and the launch mint is a namespace seed: any mint may be the namespace and any source of SOL may fund the vault (a Pump fee distribution, a Meteora or Raydium fee claim, a plain wallet transfer). Requiring a Pump bonding curve in `validate_config` would break that documented generality and refuse legitimate non-Pump vaults. The curve read belongs in the setup flow and the quote service, where a Pump launch is actually known to be the funding source.
  - **Two of the four modes pay the vault NOTHING, and both fail silently rather than reverting.** Measured on a fork: create the launch, take a 100%-to-vault fee share, run real buys, then distribute, and read the vault's lamport delta.

    | launch mode | vault SOL delta | why |
    | --- | --- | --- |
    | normal | 44,444,445 | creator fee -> creator vault -> PDA |
    | mayhem | 44,444,445 | same creator-vault path |
    | agent | 44,444,445 | same creator-vault path |
    | **cashback** | **0** | the creator-fee slice is deposited into the BUYER's `user_volume_accumulator` as `cashback_earned` (claimable by that buyer via `claim_cashback_v2`) instead of paying a creator vault |
    | **USDC-quote** | **0** | fees are paid **in USDC into a token ATA**, never as lamports |

    **A GRADUATED coin still funds the vault in native lamports** — measured, because Pump's own docs describe a WSOL hop for graduated coins ("Create WSOL ATA for sharing config authority ... `transferCreatorFeesToPump()` moves WSOL from AMM vault to pump creator vault") and that could have meant a shareholder receives WSOL into a token account instead of lamports, which would silently stop the vault funding at exactly the moment a launch succeeds. It does not: a coin bought out to `complete = true, realTokenReserves = 0` then distributed paid the vault **255,016,081 native lamports with a zero WSOL delta and no WSOL ATA even created**. The WSOL is internal plumbing between the AMM vault and the Pump creator vault; the final hop to a shareholder is a lamport transfer, matching the `COLLECT_CREATOR_FEE` doc's "a lamport transfer from `creator_vault` to `creator`". Caveat: those fees accrued on the curve that graduated, not from AMM trading afterwards, so the AMM-earned path remains unmeasured. `scripts/pm-graduated-fee-asset.ts`.
    - **SOL itself can never be a burn target** (6038, verified on chain through `validate_config`: WSOL rejected burner-attributed, JTO accepted). Solana's incinerator `1nc1nerator11111111111111111111111111111111` does genuinely destroy lamports — the account does not exist on mainnet because the runtime burns its balance every slot — but a transfer there must NOT be added to this program. It would be a FIFTH signed CPI and, whatever the destination, a withdrawal: a standalone caller-triggered lamport emission from the vault. It also turns the exact 6019 equality ("lamports out == authorized input") into a disjunction, which is precisely the guard a compromised quote authority would want loosened. It is also a different product: burning SOL benefits SOL holders by a rounding error, where this burns the target token's supply, which is what a creator is selling. If it is ever wanted, it belongs in a separate program with its own vault type. (Note: a Surfpool fork does NOT implement the incinerator's special-casing — lamports accumulate there — so this cannot be verified locally.)
    A cashback or USDC-quoted vault therefore never funds at all: no SOL arrives, so no burn is ever possible, and nothing reverts to signal it. Mayhem and agent do deliver SOL on the funding side and are excluded by scope rather than by breakage -- but "normal only" is the rule that ships, because it is a safe superset that nobody has to re-derive per mode. `scripts/pm-modes-launch.ts`.
    - Superseded claim, recorded so it is not repeated: an earlier subagent reported that every SOL-quoted mode (including cashback) delivered 44,444,445 lamports to the vault. That is FALSE for cashback, which delivers zero. The same agent's mode-as-burn-target results were also not reproducible from the scripts it left behind. Neither claim should be cited.
  - **The program cannot enforce this and must not be expected to.** `validate_launch_mint` (`token.rs`) reads exactly two things about the launch mint: that its owner is a token program, and its decimals. The mode flags do not live in the mint at all -- they live in the Pump bonding-curve PDA `PDA(["bonding-curve", mint], 6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P)`, at `is_mayhem_mode` byte 81, `is_cashback_coin` byte 82, and `quote_mint` bytes 83..115 (offsets stable across the 115-byte and post-`extend_account` 151-byte curve). Enforcement therefore belongs to the launcher / quote service: read the curve and require byte 81 == 0, byte 82 == 0, and bytes 83..115 == the System default before pointing a fee share at a vault.
  - **FUNDING is restricted to normal launches. BURNING is not restricted by launch mode at all, and must not be.** These are independent axes and conflating them has caused repeated confusion. A vault funded by a normal launch may name ANY admissible mint as a target, including a cashback or mayhem Pump coin. The target rules are exactly the ones the program already enforces and nothing more: no live freeze authority (6036), no live mint authority (6037), no unsupported Token-2022 extension (6024, i.e. Token-2022 mints that behave like plain SPL, which is what `$PUMP` is), and not a native mint (6038). There is NO mode check on targets and none should be added.
    - Measured on a fork with the launch mode held constant and the target's mode varied, classified from its own curve bytes: normal-curve targets burned 4/4, mayhem 3/4, cashback 4 of ~8, with **zero reproducible burner-attributed failures**. The transient miss is 6018 `WsolNotFullyConsumed` -- Jupiter chose a route that did not spend all the authorized WSOL, the guard correctly refused rather than stranding it, the vault was untouched, and the same coin burned on retry with a different route. That is retry-able liveness, not a defect, and is what `e2e-retry-shapes` covers. The one hard miss was Pump's own `NotEnoughTokensToBuy` on a nearly-graduated curve holding 51T tokens against a 203T buy, which fails identically for a normal coin in the same state. `scripts/pm-mode-target-matrix.ts`.
    - Separately measured with the TARGET held constant and the LAUNCH mode varied: launch mode is invisible to the burn path, as the code requires. 5 targets x 4 launch modes burned 13/20 with zero burner-attributed failures; all 7 misses were external route weather and the normal control failed in exactly the same places. `scripts/pm-launchmode-target-burn.ts`.
- The stateless vault PDA is derived from `("burner", launch_mint, target_mint)`. A funded PDA therefore has one immutable launch-to-burn-target meaning.
- A second instruction, `swap_and_burn_split`, extends that to a weighted multi-target vault: `("burner", launch_mint, target_0, .., target_{n-1}, bps_blob)`, where `bps_blob` is the little-endian `u16` weights packed in leg order. The configuration IS the address, so there is no config account, no initialise instruction, no update instruction, and no extra rent. Changing any mint, any weight, or the leg count derives a different address, which is not the address the Pump fee share points at. A funded split vault is immutable by construction, exactly as the single-target vault is.
  - The caller passes one `total_amount_in`; the program computes each leg as `total * bps_i / 10_000` with the final leg absorbing the rounding remainder, so the legs sum to the total exactly and a caller cannot redirect weight between legs. Re-weighting the call lands on a different, unfunded PDA (6012).
  - Legs must have non-zero weights summing to 10000 bps (6033), must name distinct mints (6034), and are capped at `MAX_SPLIT_TARGETS = 4` (6032). Every route account passed must belong to a leg (6006). Like any misconfiguration in a program with no withdrawal instruction, a bad config bricks the vault rather than degrading it, so a launcher must test a vault with a small burn before pointing real Pump fees at it.
  - Each leg enforces the full single-target postcondition set (WSOL conservation, per-leg lamport delta, slippage floor, burn to zero), plus a whole-call lamport check and one intermediate-balance sweep. Any leg failing reverts every leg — observed on a fork, where a completed 30 SOL JTO burn rolled back because the second leg's 70 SOL exceeded its pool.
  - The binding limit is the transaction, not the program: Solana's 64 account locks and 1232 wire bytes. Measured on a fork with address lookup tables covering the vault's own accounts: 3 legs 799-989 bytes / 37-41 locks / 150-185k CU; 4 legs 1102 bytes / 48 locks / 205-213k CU. Jupiter's `maxAccounts` (NOT `onlyDirectRoutes`, which is prohibited) is the lever that keeps routes inside the budget. A split burn always needs an explicit ComputeBudget limit above the 200k default.
- The production burn path is SOL -> WSOL -> Jupiter CPI -> configured target mint -> `BurnChecked`, atomically.
- The program must expose no withdrawal, target-update, arbitrary-transfer, fee-sharing, creator-control, or treasury-control instruction.
- Jupiter may choose unrestricted routes. Do not force direct-only routes or exclude venues without a documented, tested reason.
- **The program accepts Jupiter v2 only: `route_v2` AND `shared_accounts_route_v2`. This REVERSES the earlier fixed decision that the shared-accounts variant is refused.**
  - The v1 build accepted only `route` and refused the shared-accounts variant with 6005, and that refusal was recorded here as a deliberate security property. It is no longer one. The property the refusal actually protected -- that only an instruction whose complete account layout the burner has exactly validated ever receives the burn PDA's signature -- is PRESERVED, because the shared variant now carries its own exact, per-variant account and argument validation. A reviewer must not "restore" the 6005 shared-accounts rejection: doing so breaks every multi-hop burn, which includes the flagship own-launch-token path.
  - The variant is chosen by ROUTE SHAPE, not by the client's `useSharedAccounts` flag: a single-hop route returns `route_v2`, a multi-hop route returns `shared_accounts_route_v2`. Requesting `useSharedAccounts: false` does NOT avoid the shared path. Verified live for JTO/NEIRO/BONK (single-hop, direct) and $PUMP (multi-hop, shared).
  - The two variants have DIFFERENT layouts and are validated separately. Shared adds a leading `id: u8`, so its argument offsets are shifted by one (`in_amount` at 9 rather than 8, `platform_fee_bps` at 27, `positive_slippage_fee_bps` at 29), and its accounts sit at `[1] user_transfer_authority(signer) [2] source [5] destination [6] source_mint [7] destination_mint [8]/[9] token programs [10] event_authority`.
  - Platform-fee protection changed mechanism: v1 pinned an optional `platform_fee_account` slot to the Anchor `None` sentinel; v2 has no such slot and the program instead requires `platform_fee_bps` AND `positive_slippage_fee_bps` to be zero in the instruction data. Equivalent or stronger -- it also closes positive-slippage siphoning -- but it is a different check and 6007 now means something slightly different.
  - A pinned `JUPITER_EVENT_AUTHORITY` (`D8cy77BBepLMngZx6ZukaTff5hCt1HrWyKk3Hnd9oitf`) is now required at the variant's event-authority index.
  - Clients must pass `destinationTokenAccount` on a DIRECT route: index 7 is Jupiter's optional destination slot, and omitting it leaves the `None` sentinel there, which fails the pin with 6006. Liveness only, vault untouched.
- **A third instruction, `validate_config`, is a read-only pre-funding admission check.** The vault's config IS its address, so there is no init instruction to validate at and the admission checks otherwise run only at BURN time -- meaning anyone can derive and fund a vault whose targets can never be burned, stranding that SOL permanently. `validate_config` closes that: it runs the burn's OWN validation functions (`validate_split_leg_count`/`_weight`/`_weight_sum`, `build_split_seeds`, `derive_and_pin_split_vault`, `validate_split_target_admission`, `validate_launch_mint`), so it cannot drift from what the burn will accept.
  - It is strictly read-only: no `invoke`, no `invoke_signed`, no `Seed`/`Signer`, no lamport or data mutation, and it requires NO signer at all -- verified by walking all 26 functions in its call graph. The burn PDA still signs exactly four things. The instruction adds nothing to the custody surface because it only reads.
  - It deliberately admits a bare System account at the derived ATA address, so the intended atomic setup `[validate_config][create ATAs][fund SOL]` works in ONE transaction. Proven on a fork: a good config lands and creates all four ATAs; a bad config reverts the WHOLE transaction with no ATA created and no SOL moved. A launcher therefore cannot fund a doomed vault.
  - Limits: it proves on-chain admission at a point in time. It cannot see whether Jupiter has a route (off-chain), and it cannot prevent post-funding state changes. It replaces "derive and hope", not the mandated small test burn.
- **A native (wrapped-SOL) target mint is refused (6038 `TargetMintNative`).** WSOL and the Token-2022 native mint pass every authority and extension check -- null authorities, no extensions -- but `BurnChecked` refuses a native account and no WSOL->WSOL route exists, so such a vault is fundable and permanently unburnable. It is refused by identity in the shared `validate_target_mint`, so both the burn and `validate_config` reject it.
- Jupiter route computation remains offchain and Jupiter execution remains onchain. There is no quote-authority signature. The on-chain reference-bound floor is the price control.
- The burn PDA's signature is granted to the Jupiter CPI at EVERY route position where the account is the burn PDA, not only at `userTransferAuthority`. This reverses an earlier rule that pinned the grant to route index 1. The pin made every pre-graduation Pump token unburnable: Jupiter's Pump.fun bonding-curve route places the user at three positions (transfer authority, the curve's `user`, and the creator-fee `user`), and the two unpinned ones arrived unsigned, so Jupiter's inner CPI failed to escalate privileges. The property the pin was actually protecting is unchanged — no OTHER account's signature is ever granted, so a route can never borrow the caller's or the quote authority's signature. Because the PDA's signature at a writable position would otherwise permit lamport movement or an account reassignment, both are checked afterwards: the lamport delta is pinned to exactly the authorized input, and `verify_pda_still_a_bare_system_account` rejects a changed owner or a non-empty data buffer (6012).
- Clients must NOT pass a `payer` to Jupiter V2 `/build`: live Pump.fun and PumpSwap builds add that payer as a writable signer inside the route, which the program withholds. Fund Jupiter's setup ATAs by substituting the payer into account 0 of its idempotent-ATA-create instructions instead.
- Any swap, slippage, account-validation, Token-2022, or burn failure must revert the complete transaction and preserve the PDA's SOL and token state.
- **A target mint with a live freeze authority is refused at admission (6036 `TargetMintFreezable`).** A freeze authority can freeze the vault's target ATA at any moment; the burn then reverts forever while Pump keeps delivering fees, and with no withdrawal instruction that SOL is unrecoverable. "Permanently unburnable while still accruing" is the worst outcome this design can produce, so it is refused up front rather than discovered after a launch has locked its fee share to the address. The cost is nil in practice: every intended target has a null freeze authority (JTO, NEIRO, $PUMP, BONK, WIF, FARTCOIN, POPCAT, RAY, and Pump/Launchlab/DBC launches, all verified against mainnet). What it excludes is the centrally-freezable stablecoins, which are not burn targets. Proven both directions on live mints: USDC and USDT are rejected 6036 by the burner, and no null-freeze target is rejected by the burner.
- **A target mint with a live mint authority is refused at admission (6037 `TargetMintMintable`).** Burning a token that can be inflated afterwards does not provide the non-mintable supply reduction this product promises. The base SPL Mint `mint_authority` must therefore be `None` for both legacy SPL and Token-2022 targets. This applies only when a mint is a burn target, not when it is merely the launch namespace. META is correctly excluded; BPi and `$PUMP` remain allowed.
- The launch mint is a namespace and is NOT freeze-checked, because it is never swapped or held. It carries a different residual risk: a Token-2022 launch mint with a live `MintCloseAuthority` can be closed once its supply reaches zero, after which its owner becomes the System program and every burn fails 6010. A legacy-SPL launch mint cannot be closed and avoids this entirely.

## Rejected approaches

- Direct AMM CPI swap-and-burn (bypassing Jupiter) was prototyped on a Surfpool fork and rejected. A generic `swap_and_burn_direct` instruction — caller-supplied pool accounts plus a program-derived constant-product reserve floor — must not be reintroduced without an explicit reversal of this decision, because it is neither more secure nor better-executing than the Jupiter path:
  - The caller still selects the pool off-chain, exactly as with a Jupiter route, so it is no more trustless.
  - The reserve-derived floor is spoofable (the vaults are not proven to be the swapped pool's own reserves) and is wrong for concentrated-liquidity (Raydium CLMM, Orca Whirlpool) and bin (Meteora DLMM) venues — where JTO, $PUMP, and most established targets actually live.
  - It requires a maintained per-venue CPI adapter for every AMM (each with its own discriminator and account layout) and gives up Jupiter's routing, aggregation, and cross-venue coverage.
  - Only a derive-and-pin canonical-pool variant could be both permissionless and trustless, and only for pump-token targets with a derivable canonical pool; that remains out of scope.
- Economic and griefing red-team (custody excluded; no theft path found) surfaced findings that are the HONEST-KEY shadow of the compromised-key risk, and must be handled by OFF-CHAIN policy because the program deliberately has no clock, nonce, or admin:
  - Deterministic sandwich under an honest key. A co-signed burn transaction is complete and self-broadcasting, and the requester is baked in as fee payer, so whoever requested the co-sign can wrap `[attacker buy][vault burn][attacker sell]` in one atomic bundle and extract up to `slippage x notional`. This is worst exactly where the product points it: the own-launch majority leg routes the most SOL through the thinnest liquidity at the widest dynamic slippage. On-chain only `minimum_output` bounds it. Mitigation is operational: the quote service should submit burns privately (its own Jito bundle) rather than hand signed bytes back to the requester, sign the tightest viable slippage, cap per-burn notional, and keep at most one outstanding co-sign per vault.
  - No on-chain freshness. Nothing binds an approved transaction to a slot or nonce; it is valid for the blockhash window (~60-90s). True double-execution is stopped by the runtime's blockhash/signature dedup, and a second full-size burn reverts on balance, so this is single late execution at a stale price, bounded again by `minimum_output`. Policy: shortest viable blockhash TTL, one outstanding co-sign per vault.
  - Permanent bricks from external mint-state changes AFTER funding, all leaving the vault accruing SOL with no recovery: a target's Token-2022 transfer hook later activated (6024); a target with a live freeze authority freezing the vault ATA (6014); a Token-2022 launch mint with `MintCloseAuthority` being closed (6010). All revert with the vault's SOL preserved. These are target-admissibility decisions the launcher MUST make before funding: require freeze authority null, no active/activatable transfer hook, no live close authority on the launch mint, then the mandated small test burn. A legacy-SPL launch mint and a freeze-null target avoid all three.
  - Dust-donation liveness grief on exact-empty burns: a griefer front-runs a burn that empties the vault with a sub-rent-floor transfer, so the remainder lands in (0, floor) and reverts 6026. Vault safe, caller loses a fee. Keepers must never target exact zero; always leave >= the rent floor.
  - 6018 `WsolNotFullyConsumed` has one KNOWN BENIGN trigger, reproduced deterministically: when Jupiter V2 routes a leg through a PumpSwap pool whose coin has CASHBACK mode enabled, Jupiter's own adapter appends `ClaimCashback` + `CloseUserVolumeAccumulator` after the buy, and PumpSwap pays the just-accrued cashback IN WSOL into the vault's WSOL ATA (measured: 100,000,000 in, all consumed, then +323,770 (~32 bps) credited back). The post-route WSOL balance sits ABOVE the pre-funding snapshot, so the exact `!= wsol_before` conservation check reverts — correctly: that kickback is unaccounted value the postconditions must not silently admit. The PumpSwap `route_v2` payload (39 bytes, variant 0x93) has NO `track_volume` byte, unlike the raw curve's 40-byte 0x98, so there is no client-side off-switch. Vault untouched, and transient by construction: a re-quote that lands on any other venue burns clean — proven by `scripts/e2e-6018-cashback-retry.ts` (`npm run test:6018`), which provokes a real burner-attributed 6018, asserts nothing moved, then burns the SAME vault via a non-Pump route. The quote service should treat burner-6018 as retryable and rebuild the leg with `excludeDexes: ["Pump.fun Amm","Pump.fun"]` (a documented venue exclusion, NOT the prohibited `onlyDirectRoutes`); do NOT loosen the on-chain check or admit the cashback credit. The raw-curve analogue (pump.fun `claim_cashback_v2`) is documented but unproven live — both observed mints graduated before it could be isolated — so the harness's 6019 `track_volume` clear was deliberately NOT extended to 6018.
  - Jupiter v6 is upgradeable and pinned only by id, so a malicious Jupiter UPGRADE is the realistic path to the "hostile program at the pinned Jupiter id" that the 6035/6012/WSOL postconditions defend against. Inherent to CPI-ing an aggregator; names an operational risk, not a fixable code path.
- The production burn path therefore stays SOL -> WSOL -> Jupiter CPI -> configured target mint -> `BurnChecked`, gated by the quote-authority signature. The quote authority cannot withdraw or redirect custody — the lamport-delta and WSOL postconditions prevent the PDA from emitting SOL to an arbitrary address — but it can approve a bad price: a compromised authority can co-sign `minimum_output = 1` with a valid route and cause economic loss up to the amount being burned in that transaction. Loss is bounded by the minimum output it signs, not by zero. If the key is offline, burns merely pause and the vault's SOL stays safe. A leaked key is worse than "degraded execution" and must be treated as loss of the funds being burned: a red-team exercise on a Surfpool fork landed a real transaction signing `minimum_output = 1`, draining a vault and destroying the output as a burn, and repeating that call drains a vault to zero. Worse, an attacker who also supplies liquidity in the Jupiter route can route the swap through a pool they control at a punitive price and capture that value as an LP rather than merely losing it to the market. No account substitution, redirect, or withdrawal path was reachable in that exercise — custody held under direct attack — but "cannot steal" is only true of custody, not of value.

## Required validation

- Test the complete flow on a Surfpool mainnet fork: Pump token creation, SOL delivered to its paired burner PDA, Jupiter swap, and on-chain burn.
- Test JTO target mint `jtojtomepa8beP8AuQc6eXt5FriJwfFMwQx2v2f9mCL`.
- **Every launchpad and pool venue burns. Measured on the fork with every failure attributed to the program that raised it; the bar is zero BURNER-attributed failures.**
  - Pool AMMs (Raydium, Raydium CLMM/CP, Whirlpool/Orca, Meteora DLMM/DAMM v2), blue chips (JTO, NEIRO, $PUMP Token-2022, BONK, WIF, FARTCOIN, POPCAT, RAY), **Raydium Launchlab**, **Meteora Dynamic Bonding Curve**, **PumpSwap** (4/4), and the **raw Pump.fun bonding curve** (7/8, the miss being Jupiter's own slippage error) all burn with **0 burner-attributed failures**.
  - Pump venues require THREE client-side pre-payments, none of which weaken the lamport guard. All are paid by the caller and none need the vault's signature:
    - `init_user_volume_accumulator` on both Pump programs — `PDA(["user_volume_accumulator", vault])`. Discriminator `[94,6,202,115,255,96,232,183]`, identical on Pump.fun and PumpSwap. Takes `payer` as signer and `user` as a plain NON-signing pubkey, so a third party can create the vault's accumulator for it. Jupiter V2 closes the venue-specific accumulator after each buy and refunds its exact 1,844,400 lamports to the vault. The program admits that credit only after snapshotting the exact derived, Pump-owned, correctly discriminated account with stored user equal to the burn PDA, then requiring it to be System-owned, empty, and zero-lamport after Jupiter. Conservation remains exact: `after = before - authorized_input + validated_closed_account_credit`. The caller must recreate the accumulator before the next Pump-venue burn.
    - Every missing associated-token-account the route names, in practice the venue's creator-fee vaults. An ATA address is a pure function of (owner, mint, token program), so pre-creating one can only bring into existence the exact account the route already named.
    - `extend_account` on Pump.fun — the fix for what looked like an intermittent raw-curve failure. Pump's `BondingCurve` struct grew 115 -> 151 bytes in a program upgrade and older curves are migrated LAZILY: the first buy after the upgrade reallocs +36 bytes and bills the BUYER 250_560 lamports (36 x 3480 x 2). That is per TOKEN, not per vault, which is exactly why only some tokens failed. `extend_account` (discriminator `[234,102,194,203,150,72,62,229]`, accounts `[bonding_curve (w), user (s,w), system, event_authority, program]`) carries NO authority constraint tying `user` to `account`, so any third party can migrate any token's curve. Send it unconditionally: on an already-current curve it is a no-op costing only the transaction fee, and hard-coding the current size would rot the moment Pump grows the struct again — the on-chain size is already ahead of the published IDL.
  - The 6019 lamport postcondition remains exact. No tolerance was added: only the fully validated, fully closed Pump accumulator's snapshotted balance enters the conservation equation; every other lamport movement still fails 6019.
- A brand-new Pump mint has no Jupiter route at all (`TOKEN_NOT_TRADABLE`) until Jupiter indexes it. That is a Jupiter indexing property, not a burner limitation: the burn simply fails and can be retried later, with the vault's SOL untouched.
- **Setup rent is paid by whoever sets the vault up, and most of it is locked forever. This is a cost, not a defect, and no close path should be added.**
  - Measured per vault against the deployed programs: WSOL ATA 2,039,280; each legacy target ATA 2,039,280; a Token-2022 target ATA 2,074,080-2,108,880 (measured, not computed -- $PUMP's is 175 bytes); each Pump `user_volume_accumulator` 1,844,400 on each of the two Pump programs; a per-vault address lookup table 2,394,240 (1 leg) to 3,730,560 (4 legs). Flagship 3-leg config totals ~0.0152 SOL, and a 1-leg non-Pump vault ~0.0041 SOL.
  - The vault's ATAs can NEVER be closed. Closing needs the owner's signature, the owner is the PDA, and no token-account `CloseAccount` appears in the burner. (Jupiter's own wallet flow shows the contrast: with `wrapAndUnwrapSol` a NORMAL wallet's WSOL account is created and closed inside the swap transaction, signed by the wallet, so wallets get that rent back every time -- the vault deliberately cannot replicate that, which is why its WSOL rent is a one-time locked cost instead.) The delegated-close channel is foreclosed by 6035, deliberately: the powers that could reclaim this rent are the same powers that could drain the account. Pump volume accumulators are different program-owned PDAs: Jupiter V2 closes the exact venue accumulator through Pump using the vault's route signature and returns its precisely accounted rent to the vault.
  - Do NOT add a close instruction. Refunding to the caller is rent theft from the launcher plus a burn-bricking grief; refunding into the PDA is circular, because the reclaimed SOL can only leave via a burn, which needs the very ATAs just closed. Either way a fifth signed CPI re-opens every custody review for ~0.012 SOL a vault. The signing surface staying closed is what the audit result rests on.
  - Client-flow waste that WAS fixed, recovering real money without touching the program: the lookup tables are no longer frozen (a frozen table can never be deactivated, so its rent is locked forever -- and freezing buys nothing, since entries are immutable once written, the quote authority's signature pins the table and indexes, and anyone can build a substitute table); the Pump accumulators are created only for vaults with a Pump-ecosystem target; a 1-leg vault gets no per-vault table; and `extend_account` is skipped for graduated bonding curves. Verified: an unfrozen table deactivates successfully and a 3-leg burn still lands at 40 locks. A one-transaction variant folding the vault-ATA creates into the burn transaction itself was prototyped pre-V2 (rentexp q1) and fit the wire/lock budget at 2-3 legs (~1064 bytes / 44 locks), but was never adopted or re-proven under V2 and saves no rent, only one transaction; setup stays a separate transaction, made safe by `validate_config`'s atomic [validate][create ATAs][fund] flow.
- **A Pump fee share is immutable once set — proven, not assumed.** On a fork, `updateFeeSharesV2` pointed a fresh launch's fees at a vault, and every subsequent re-point attempt (all three plausible `currentShareholders` shapes) was refused by Pump's own program with 0x1779. A creator therefore gets exactly one shot at pointing the fee share, which is why the measured atomic grouping `[fee config][fee share][validate_config][create ATAs]` (fits: 1,039-1,229 bytes at 1-3 legs) matters: the fee share can only be committed in the same transaction that proves the vault admissible, so a doomed vault can never end up with a live fee share.
- The vault is an ordinary System-owned account, so ANY source of SOL funds it -- a Pump fee distribution, a Meteora or Raydium fee claim, or a plain transfer from any wallet. The program reads only the PDA's lamport balance and has no notion of provenance; every fork test funds vaults with a bare `SystemProgram.transfer`. Likewise `launch_mint` is a namespace seed only: any valid mint works, and the targets may be any Jupiter-routable mint on any venue.
- **Compute, not wire size, is the binding constraint on a live 3-leg burn, and it is ROUTE VARIANCE rather than configuration.** Measured on a fresh fork across 26 burns: the same config that exhausted the 1,400,000 CU ceiling burned 4/4 on retry with a fresh quote (~991k CU), and a sweep of the $PUMP leg from 10% to 70% burned 6/6 with CU ranging 576,996-991,633 and NO correlation to the split. Jupiter returns a different route per `/build` call; occasionally one is deep enough to exhaust the budget. Do NOT mis-diagnose this as a configuration limit.
  - Route width is therefore a COMPUTE lever as well as a wire-size one. One RAY leg at an uncapped 53 locks exhausts the budget; the same leg at `maxAccounts=24` burns using 1,302,852 CU and at 16 uses 906,746. `runSplitCase` previously narrowed the route only on BYTE overflow, so a transaction that fit the wire but exhausted compute simply failed; it now narrows on compute exhaustion too, recording `computeNarrowedTo`.
  - The production quote service should retry a CU exhaustion with a fresh quote for the same reason. The demo service already does (`MAX_BURN_ATTEMPTS`), retrying only externally-attributed failures and never a burner-attributed one, which is deterministic.
  - Matrix result, 12 three-leg cases across varied targets and splits on a fresh fork: **10/12 landed with ZERO burner-attributed failures**, and both misses landed 4/4 on retry. Every failure was CU exhaustion. `scripts/pm-burn-matrix-3leg.ts`.
  - **`FORK_DEX_PROFILE=pool` is mandatory for any fork burn measurement.** Without it Jupiter routes through market-maker / RFQ venues that quote off private state a fork has no copy of, and they fail with venue-specific errors (`0xfaded` and similar) that have nothing to do with the burner. Two measurement runs in this project were invalidated by exactly that omission and wrongly reported as burner faults.
  - A fork left running for ~2 days drifts far enough from mainnet that even single-leg burns fail (Orca Whirlpool `InvalidTimestamp` and `InvalidTickArraySequence`, Jupiter `0x1771` slippage against frozen pools). Restart the fork before trusting any burn measurement.
- **The one-transaction vault setup is limited by how many DISTINCT MINTS the transaction touches, which is not the same as the leg count.** The shipped product is ALWAYS three targets (or two when merged) and never four — but the setup transaction also contains the LAUNCH MINT, because it is the fee-share subject. So the distinct-mint count is three when the creator's 70% pick IS their launch token, and four when it is some other token. Measured for `[createFeeSharingConfig][updateFeeSharesV2][validate_config][create ATAs]` against the 1232-byte limit, all with exactly three legs: creator picks their OWN token → **1,229 bytes / 28 locks (fits)**; creator picks a different token, so the launch mint is a fourth distinct mint → **1,261 bytes / 29 locks (29 OVER)**; the merged two-leg shape → 1,182 bytes. Naming the launch mint as a target costs only an ATA rather than another 32-byte account lock, which is why the frontend defaults the creator's pick to their own token. When it does not fit, setup splits into `[validate_config][create ATAs]` then `[fee config][fee share][validate_config]`: `validate_config` is deliberately repeated in the SECOND transaction so the irreversible fee share is still gated by a validate running in its own transaction, not by trusting the earlier one.
- Jupiter's `maxAccounts` is a client-side FITTING lever, not a requirement: Jupiter routes fine without it, and the program never sees it. It is needed because live mainnet routes run 18-56 accounts per leg against a 64 account-lock ceiling. Verified against live mainnet at slot 440516177 (solana-core 4.2.0) by `scripts/split-mainnet-sim.ts` -- the V2 rewrite; the pre-V2 checker under that name asserted the retired v1 `route` discriminator and v1 platform-fee `None` sentinel (a shape the program now refuses with 6005) and was deleted for running green against something that no longer exists. Prefer attempting uncapped and capping only on overflow -- uncapped 1-leg (17 locks) and 3-leg (43 locks) burns both land.
